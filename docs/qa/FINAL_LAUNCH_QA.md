## Hybrid Keyboard-Language Integration — iOS and Android

**Priority: nonblocking prelaunch enhancement.** Continue critical launch QA even if this enhancement remains under review or device verification.

- Separate typing-language choices from app display language and message translation preferences. Default to system keyboard behavior. Scope a saved choice to the signed-in account and conversation; do not infer language from message content or contacts.
- iOS: use a stable UIKit `textInputContextIdentifier` for each conversation so the system can remember a keyboard selected manually. A language choice creates a separate memory context; it does not select or force a keyboard.
- Android: send the explicit choice through Compose `KeyboardOptions.hintLocales`/`EditorInfo.hintLocales`. Clear the hint for system behavior. The active IME may ignore the hint.
- Focused automated checks: preference persistence and account/conversation isolation; choice changes and clearing; distinct context/hints when switching conversations; draft/delegate binding; app-language independence. Complete composer multiline/send and translation UI behavior still need hands-on checks.
- Localization review: the menu reuses existing translated language names for all 147 choices. All 715 previously missing keyboard-copy entries (429 iOS, 286 Android) now have AI-generated, structurally validated translations in isolated feature branches; no paid translation API or DeepL was used. The 15 earlier Spanish, French, and Portuguese drafts were preserved unchanged. All 730 non-English keyboard entries remain **linguistically unreviewed**, with provenance recorded in each mobile branch's `docs/qa/KEYBOARD_AI_TRANSLATIONS.json` for the new 715. A second-pass risk scan and 172-entry back-translation sample led to 12 targeted corrections; 126 entries retain uncertainty flags, including 47 variant-sensitive entries. iOS uses the string-catalog `needs_review` state, and Android uses unreviewed resource comments. iOS simulator and Android resource tests found no English fallback for the new strings across the 147 app-language choices; Android required keyboard-only legacy resource aliases for `he`/`iw`, `id`/`in`, and `yi`/`ji`. This is automated coverage, not native-speaker approval. Keep the enhancement nonblocking if further language review would delay critical launch QA.
- **Physical-device verification still required:** with at least two installed keyboards, switch languages manually in two conversations, leave/reopen each, and confirm keyboard behavior without a forced switch. Test system choice, a manual override, and an unavailable keyboard/IME language. Check a third-party Android IME, hardware keyboard, accessibility labels and VoiceOver/TalkBack, draft editing/selection, attachment caption, and send stability. Sample Simplified/Traditional Chinese, Kurmanji, Meitei, Dari, and Brazilian/generic Portuguese where installed; verify the app language and translation preference stay independent. Record keyboard/IME and OS versions and whether each IME honored the hint; do not describe best-effort behavior as guaranteed automatic switching.

### Supported-language audit, November 11

- The iOS `AppLanguages.all` and Android `LANGUAGES` menus each contain 147 distinct choices. Focused tests iterate every choice: iOS preserves 147 distinct conversation context identifiers; Android persists every choice and produces a parseable IME locale tag. Unsupported saved codes produce no Android hint or an iOS system context. Mixed case and underscores normalize to each platform's menu code.
- Android sends script-first hints for `zh-CN`/`zh-TW` (`zh-Hans-CN`/`zh-Hant-TW`) with the region tags as fallbacks; `ku` (labeled Kurmanji) sends `kmr` then `ku`; `no` sends `nb` then `no`, matching the existing app-locale choice. `mni-Mtei` keeps its script. Android `pt` remains generic and rejects `pt-BR` as an unsupported menu choice; iOS `pt-BR` remains Brazilian and does not accept generic `pt`. Do not silently equate those Portuguese choices.
- Source localization assets use additional aliases: the built iOS string catalog has `ku`/`fil` but no exact `kmr`/`tl`; Android resources have `values-kmr`, `values-nb`, and `values-fa-rAF` but no exact `values-ku`, `values-no`, or `values-prs`. Android also uses generic `values-mni` for menu code `mni-Mtei`. The Android app-locale helper maps `no`, `prs`, and `mni-Mtei` to those resources, but has no explicit `ku` mapping. Review these display-language/resource mappings separately; the keyboard hint preserves `mni-Mtei` and does not alter app or message translation preferences.
- A parseable tag or distinct context does **not** establish an installed keyboard, its writing-system variant, or IME compliance. Generic choices such as `sr`, `pa`, and `ar` do not select a script or region; the user remains in control of the keyboard.

Current status: iOS #79, Android #107, and main-repository #327 are merged; physical-device verification remains outstanding. The November 12 integration review corrected 18 further meaning or clarity errors, including a reversed Kurmanji warning, and recorded specific handling for all 47 variant-sensitive entries. The 126 uncertainty flags remain as optional targeted linguistic-review leads, including low-confidence Tamazight, Samoan, Wolof, Tok Pisin, and Dhivehi wording; no entry is marked human-approved. After these corrections, the Android unit suite passed (301/301) with Kotlin/resource compilation and the iOS simulator focused XCTest passed (8/8) with the app test build. These checks cover all menu codes and new string lookup, storage isolation, clearing/system behavior, context changes, draft/delegate stability, and app-language independence. They do **not** prove that a particular keyboard honors a hint or that the complete composer UI works on every device. This checklist does not authorize app publication or production changes.
