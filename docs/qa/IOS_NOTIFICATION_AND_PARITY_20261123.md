## Approved notification behavior and release dependency

The backend candidate `3b3e3708cf5ff6125e2264e63c3ab4c45ddc7876` adds the persisted SMS `messageId` to APNs/FCM data after successful persistence. Existing clients ignore the additive field. Older SMS pushes without an ID remain readable but cannot be reliably correlated with socket events. **Deploy the backend first**, using a separately approved commit-bound package; distribute iOS only after its own review and device QA. No migration or forwarding quiet-hours change is included.

On iOS, APNs owns audio and retains the backend-selected custom notification tone and OS Focus behavior. A socket-only foreground delivery can show a localized, generic, in-app banner after a 1.2-second grace period when the actual screen calls for a banner. This banner has no decrypted message content or background delivery; late APNs cannot create a second banner. When APNs never arrives, the socket-only fallback has no tone by design. This is a delivery limitation to verify on devices, not a claim that APNs is guaranteed. A displayed in-app fallback is dismissed on account, tab, conversation, or foreground-state changes; a pending fallback rechecks the actual screen before presentation and is canceled on account/background changes. Accessibility visual alerts use their existing preference and are deduplicated by account, channel, and message ID. The ledger is bounded to 512 keys and a five-minute idle lifetime; events beyond that window can be treated as new.

There is no separate per-conversation notification mute or message-alert quiet-hours policy established by this code. Do not reuse call/text forwarding quiet hours as a notification setting.

Strict enforcement requires separate approval and production verification before public launch. No existing Device timestamp or token is treated as proof of authority.

Implementation, automated verification, and physical-device/browser evidence remain separate. An offline local sign-out is not known to the server until cleanup reaches it or the session expires. APNs/FCM submissions already accepted or in flight cannot be recalled. Legacy registrations without a verifiable session must fail closed at strict activation; older clients may lose notifications until they update and authenticate. The foreground sound/banner correction and push client were integrated together in iOS PR #102. Random Chat's proposed migration 167 and MLS schema work require their own migration-package reconciliation after this security-first release; neither is included here.

The reviewed iOS integration candidate was `c258ac0fb76f04f5a9f5b08550c212e8e9e16f41`, including a test-only race-scheduling correction. PR #102 squash-merged it at `317c8756fef356bd194ad47084ae4e020512965a`; the merged tree exactly matched the reviewed tree. The unrelated generated `Localizable.xcstrings` worktree change was excluded and preserved separately for inspection. Earlier integration evidence recorded push authority 9/9, affected regressions 109/109, and a passing Release simulator build. These are simulator results; APNs, VoIP, logout, account switching, and notification presentation on a physical device remain unverified. The separate backend migration and strict activation remain undeployed and require their own approval.

The isolated backend API is `POST /devices/push-authority/activate` with a full authenticated session (the short `/auth/token` credential is ineligible for push authority) and `{installationId, installationProof, deviceId, platform, appId}`. The client generates one random UUID and 32-byte base64url proof per app installation and retains them in account-independent secure device storage. Activation returns `{generation, expiresAt, cleanupCapability}`. `POST /devices/push-authority/register` requires the same installation identity, the current generation, `{provider, environment, token, tokenRevision}`, and the current authenticated session. iOS registers `apns` and `apns_voip` independently with `production` or `sandbox`; Android uses `fcm` with `none`. The client increases `tokenRevision` on token replacement. `POST /devices/push-authority/cleanup` accepts only `{installationId, generation, cleanupCapability}`, requires no JWT, returns 204, and cannot read account or message data. Store the cleanup capability in secure storage for offline retry; erase it after confirmed cleanup or when a later generation supersedes it. Do not store or transmit the raw session JWT as a cleanup capability.

Explicit `POST /auth/logout` and `GET /auth/logout` now revoke push grants for the presented signed **full** session and record its SHA-256 fingerprint before returning success or redirecting; repeating full-session logout is safe. A short `/auth/token` credential is not bound to its parent full session and receives `401 full_session_required` at either logout endpoint. Authenticated `POST /devices/logout` likewise requires a full session (`401 FULL_SESSION_REQUIRED` for a short token), uses the same session fence while clearing the specified device, and a stale device-logout request cannot clear a newer session's device. A delayed request using a logged-out JWT cannot activate or register under either its old or a new installation ID. The backend retains the fingerprint through session expiry plus 24 hours, then prunes it through a restricted database function; no raw JWT is stored. A logout does not revoke another independently authorized session on another device or browser. iOS must use its full session for confirmed authenticated logout; a short-token rejection is not confirmed server cleanup. It should still use the generation-bound cleanup capability when its JWT has expired, a 401 prevents authenticated device logout, or it signs out offline and retries later. A failed server request cannot be treated as confirmed server cleanup. When a token transfers between distinct installation IDs, the prior installation generation is fenced; the client should retain one stable installation ID across account changes and reauthenticate before claiming a token held by a newer session. Session-issuing MFA setup, enable, and disable require an unrevoked full session; reauthentication through the ordinary sign-in/MFA challenge remains available after logout.

The proposed migration `20261124020000_push_session_authority` follows the verified 166 baseline and is **not approved for production execution**. The new table grants are limited to SELECT/INSERT/UPDATE for the restricted API role. Existing 166 migrations stay byte-identical. The historical Random Chat proposal called its migration 167; its owner must reconcile name, order, package manifest, and dependencies after this security migration. MLS schema work likewise needs a separate rebase and package review. The additive backend defaults to shadow mode, where legacy delivery remains available; activate strict mode only after approved client registration, production grant checks, and a separately approved rollout. A rollback to legacy token dispatch would reintroduce the signed-out-device privacy exposure and needs explicit risk acceptance.

The browser Twilio Voice identity is separate from native APNs/FCM registrations. Its short-lived Voice token and socket teardown require independent web-session verification before claiming full cross-platform notification authorization. No account data is inferred from legacy `Device.lastSeenAt`, `updatedAt`, or a retained token. A server-side check immediately before provider submission narrows, but cannot eliminate, the window for a revocation concurrent with an already in-flight provider request.

### Separate pre-launch authentication correction

The independent audit confirmed that an explicitly logged-out full JWT remains usable for ordinary authenticated API and socket access until its normal expiry, although PR #350 prevents that JWT from reestablishing push authority. This is a separate demonstrated security blocker for public launch. The isolated backend checkpoint `fix/session-revocation-api-socket-20261124` at `0fbaaabfb9d0e1231dbf9420d287226e935f9f12` now checks the existing durable `PushSessionRevocation` fingerprint in shared API middleware and the active Socket.IO handshake, inbound packets, and a five-second idle recheck. Explicit logout disconnects that session's socket room; other sessions remain authorized. New short tokens are issued only from an unrevoked full session and carry a signed parent-session fingerprint and expiry. Legacy unbound short tokens are rejected immediately; clients with only such a token must use their full session or sign in again. This is an availability tradeoff for up to the old token's ten-minute lifetime, made to avoid continued access after logout. The local checkpoint passed 81/81 focused unit and synthetic HTTP/socket tests. It is **not merged or deployed**. No schema or migration change was made. Rollout requires PR #350's migration and runtime grants first, and immediate cross-node socket teardown requires a functioning Socket.IO Redis adapter where multiple API nodes are used; in-flight packets cannot be recalled. Android and web must clear local credentials, tear down sockets, and reject stale alerts on sign-out; implementation and verification remain U until evidenced.
