# iOS notification correction and cross-platform QA parity

Status: review candidate, November 23, 2026. This document does not replace the launch checklist, existing QA receipts, or physical-device signoffs. A merged source change is not evidence that a particular distributed build or deployed web/backend release contains it.

## Approved notification behavior

| App state                                        | SMS and Chatforia incoming message                                                                  | Required checks                                               |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Receiving conversation visible                   | Update its message and read state; no redundant banner; at most one eligible tone                   | Both channels, APNs/socket arrival order, read acknowledgment |
| Chats list visible                               | Update preview and authoritative unread/badge state; no redundant banner; at most one eligible tone | Both channels, duplicate events, translated SMS preview       |
| Different conversation or Calls/Contacts/Profile | One foreground banner and at most one eligible tone                                                 | Both channels, navigation and stale visibility                |
| Background or locked                             | Preserve native OS notification behavior                                                            | Real device, custom tone, silent/vibrate, Focus               |

Foreground audio, banners, and accessibility visual alerts must be deduplicated by authenticated account, channel, and persisted message ID. The iOS socket fallback requests a sound-only native notification with the existing account-selected tone; the APNs path retains the backend-selected tone. The backend SMS APNs payload gains an additive `messageId`; older clients ignore it. Existing SMS pushes without an ID remain readable by newer clients but cannot be reliably correlated with socket events. Deploy the backend before distributing the iOS correction. No forwarding quiet-hours setting is reused as a notification preference. Current code does not establish a separate per-conversation notification mute or message-alert quiet-hours policy; confirm any such product requirement independently.

## Android and web notification parity tasks

- Android has `ChatforiaFirebaseMessagingService.kt`, `NotificationCoordinator.kt`, and `SocketManager.kt` SMS events. Review FCM notification/data handling, socket tone playback, active conversation/tab state, and message-ID dedup independently. Confirm notification channels and OS Do Not Disturb behavior on devices; do not port iOS presentation APIs literally.
- Web has socket listeners, browser notifications, `CallManager.jsx` sound playback, and `visualAlerts.js`. Review browser visibility/focus permissions, service-worker notification behavior, account-scoped event IDs, and tab/conversation state. Browser autoplay and OS notification controls differ from iOS.
- Neither Android nor web received an implementation change in this workstream. Their status remains **parity not verified** until separate code review, tests, and device/browser QA.
